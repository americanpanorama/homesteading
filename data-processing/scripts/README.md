# Core App Data Pipeline

This directory contains the scripts that appear to generate the main app data.

It also contains older duplicates and one-off helpers, so this README focuses on the files that look most relevant to the current app.

## Layout

The directory is now organized like this:

- root of `scripts/`: core pipeline scripts
- `diagnostics/`: debugging and inspection helpers
- `one-time/`: migration/cleanup scripts that were likely run manually
- `reports/`: summary/export scripts that are not part of the core build
- `scripts/`: older duplicate subtree kept as legacy reference

If you are trying to understand the pipeline, read these files in this order:

## Recommended Pipeline Order

If the goal is to rebuild app data from source inputs, this is the best reconstruction of the order:

1. Optional data cleanup/update
2. Generate yearly map data and office/district outputs
3. Generate state and office timeline data
4. Rebuild place year ranges from the canonical published timeline data
5. Publish outputs into the locations and shapes the app actually reads

The last step is real: some scripts stop at `build/data`, while the app reads from `public/data`.

## Script Notes

### `createYearGeojsonFilesWithClashes.ts`

This looks like the main generator for yearly map data.

It reads:

- `../data-input/townshipssimplified.json`
- `../data-input/townships_data.json`
- `../data-input/GLOs.json`
- `../data-input/clashes_updated.json`

It writes:

- `../../build/data/yearData/<year>.json`
- `../../public/data/yearData/<year>.json`
- `../../build/data/districtsData/<office>-<state>.json`
- `../data-input/conflictsDataWithOffices.json`

What it does:

- organizes township data by fiscal year
- matches office/year data to spatial township boundaries
- handles special full-state offices via `GLOs.json`
- redistributes data for districts that ended before the fiscal year end using `adjustedForMap`
- performs redistribution after every office for the year has been instantiated, so allocations do not depend on source-row order
- normalizes pre-1889 North and South Dakota geography to Dakota Territory for June 30 allocation
- fails generation if a closed office cannot be allocated or if adjusted map totals do not conserve every state-year metric
- attaches clashes/conflicts to offices and years
- writes district boundary data for minimaps and office views

The nested output is an intentional intermediate representation:

This script still works with a nested office shape:

- `data: [...]`
- `office_boundaries: [...]`

`publishBuildData.mjs` converts that intermediate representation to the flattened shape checked into `public/data/yearData`. It selects the boundary active on June 30 and the `adjustedForMap` metrics when an office transition required allocation.

The generator also writes allocation and conservation diagnostics under `DIAGNOSTICS_ROOT`:

- `mapDataAllocations.json`
- `mapDataConservation.json`

### `makeStateTimelineData.ts`

This script aggregates yearly office data into timeline files.

It reads:

- `../../build/data/yearData/<year>.json`
- `../data-input/conflictsDataWithOffices.json`

It writes:

- `../../build/data/timelineData/<STATE>.json`
- `../../build/data/timelineData/national.json`

What it does:

- groups office data by state/territory
- builds per-office `yearData` arrays
- attaches conflicts to the appropriate fiscal year
- computes median year by claimed acres
- aggregates office timelines into state/territory timelines

Important caveat:

This script also assumes the nested office shape generated by `createYearGeojsonFilesWithClashes.ts`.

It writes to `build/data/timelineData`; `publishBuildData.mjs` then copies those raw reported-office timelines to `public/data/timelineData`.

### `createYearRangeForPlaces.ts`

This script generates the place availability/routing range file.

It reads:

- `../../public/data/timelineData/national.json`
- `../../public/data/timelineData/<STATE>.json`

It writes:

- `../../data/placesDateRanges.json`

What it does:

- scans the canonical published timeline data
- determines first and last year for each state/territory and office
- writes a compact lookup used by the app to know when places exist

This is now the authoritative source for route availability. It intentionally
derives from the canonical timeline data so router validation matches the app's
published data.

### `buildPlacesDateRanges.mjs`

This wrapper compiles and runs `createYearRangeForPlaces.ts` in a way that
works on the current Node version.

It exists because the older `ts-node/esm` setup in `data-processing/` is not
reliable under the current local toolchain.

Use it like this:

```bash
cd data-processing
npm run build-places-date-ranges
```

Or from the repo root:

```bash
npm run build-places-date-ranges
```

Recommended usage:

- rerun it after regenerating `public/data/timelineData`
- rerun it before testing route-driven place selection bugs

### `diagnostics/auditPlacesDateRanges.mjs`

This diagnostic checks `data/placesDateRanges.json` against the canonical
published timeline data under `public/data/timelineData`.

It exits non-zero if any state or office ranges drift from the published
timeline data.

Use it like this:

```bash
cd data-processing
npm run audit-places-date-ranges
```

Or from the repo root:

```bash
npm run audit-places-date-ranges
```

Recommended usage:

- run it after `npm run build-places-date-ranges`
- run it after regenerating `public/data/timelineData`
- use it as the first check when a route-selectable state or office fails to load

### `publishBuildData.mjs`

This script is the missing publish step between generated `build/data` outputs
and app-facing `public/data` files.

It:

- flattens `build/data/yearData/*.json` into the office shape the app reads
- copies `build/data/timelineData/*.json` into `public/data/timelineData`
- syncs the legacy `public/timelineData` mirror from the same generated timeline data
- copies `build/data/districtsData/*.json` into `public/data/districtsData`
- also copies `indianLandsYearData` and `yearGeojson` if they exist in `build/data`

Example usage:

```bash
node data-processing/scripts/publishBuildData.mjs
```

Optional modes:

```bash
YEAR_DATA_MODE=map node data-processing/scripts/publishBuildData.mjs
YEAR_DATA_MODE=raw node data-processing/scripts/publishBuildData.mjs
```

Mode behavior:

- `map` (default): prefers `adjustedForMap` values when flattening `yearData`
- `raw`: prefers the original non-adjusted office totals

Use `map` for app-facing publication.
Use `raw` when doing strict diagnostic comparisons against office-level timeline files.

The production build now also copies `public/data/timelineData` into
`build/timelineData`, so the legacy build-time timeline tree stays aligned with
the canonical app-facing data.

### `one-time/updateWith1908-10Data.ts`

This script appears to patch in corrected Indian claims data for 1908-1910.

It reads:

- `../data-input/townships_data.json`
- `../data-input/IndianClaims1908_1910.json`

It writes:

- nothing directly to disk
- the merged JSON is printed to stdout

This means the intended usage was probably something like:

```bash
cd data-processing
node --loader ts-node/esm scripts/one-time/updateWith1908-10Data.ts > data-input/townships_data_updated.json
```

That redirection step is not baked into the script.

### `one-time/clearnTownshipsData.ts`

The filename has a typo, but the purpose is fairly clear: normalize townships tabular data.

It reads:

- `../data-input/townships_data2.json`
- `../data-input/townships_data.json`

It writes:

- `../data-input/townships_data_cleaned.json`

What it appears to do:

- normalize office/state naming
- preserve the old `of_id`
- collapse fields into a cleaner schema

This looks like a prep or migration script rather than part of the core runtime pipeline.

## Other Files Worth Knowing About

### `diagnostics/runTrialRegeneration.mjs`

This wrapper exists specifically to make safe comparisons easier.

It:

- compiles the current TypeScript generators into a temporary run root
- mirrors just enough of the workspace layout for the legacy scripts to run
- writes outputs into temporary `build/data` and `public/data` trees
- leaves the checked-in app data unchanged

Example usage:

```bash
node data-processing/scripts/diagnostics/runTrialRegeneration.mjs 1868,1902
```

This is the best starting point if you want to answer:

- "what would the current pipeline generate today"

without replacing checked-in data.

### `diagnostics/runRegenerationComparison.mjs`

This wrapper goes one step further than the trial runner.

It:

- refreshes the published mismatch audits
- runs a safe regeneration into a temporary output tree
- audits the regenerated outputs
- writes a summary comparing published mismatch counts to regenerated mismatch counts

Example usage:

```bash
node data-processing/scripts/diagnostics/runRegenerationComparison.mjs
```

The default is the full `1863-1912` range. You can also pass a smaller list of
years if you want a faster targeted comparison.

### `diagnostics/auditPublishedDataConsistency.mjs`

This is a new repeatable audit script created during the 2026 documentation pass.

It compares:

It writes:

- `../reports/published-data-audit.md`
- `../reports/published-data-audit.json`

This is currently the fastest way to see where the checked-in published outputs disagree.

### `diagnostics/auditPublishedOfficeTimelineConsistency.mjs`

This is the office-level companion to the state-level audit.

It compares:

- `public/data/yearData/*.json`
- `public/data/timelineData/<STATE>.json`

It writes:

- `../reports/published-office-audit.md`
- `../reports/published-office-audit.json`

This is the fastest way to tell whether a mismatch is already present at the
office level or only appears after state aggregation.

## Files That Look Legacy Or Duplicated

These should be treated with caution:

- `createYearGeojsonFilesWithClashes (original).ts`
- `scripts/scripts/...`
- `diagnostics/dataWithoutTiles.json`
- `diagnostics/readableDistricts.json`
- `diagnostics/readableSpatialData.json`

The `scripts/scripts/` subtree appears to be an older copy of many files in this directory.

The current evidence suggests that those legacy scripts may not be merely
historical duplicates. At least some checked-in published `yearData` output
appears more consistent with their stricter matching behavior than with the
current top-level generator script.

## Running The TypeScript Scripts

There is no polished build CLI here. The package does include `ts-node`, so the likely invocation pattern is:

```bash
cd data-processing
node --loader ts-node/esm scripts/<script>.ts
```

That said, do not assume rerunning the pipeline will reproduce the checked-in `public/data` outputs without first resolving the shape and publication discrepancies documented in the top-level README.
